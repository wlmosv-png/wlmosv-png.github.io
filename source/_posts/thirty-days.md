TGAutoSign 是我写的 Telegram 自动签到模块，走 LSPosed 分发。发版一段时间之后，我一直在看三个数：**141、64、13**。

## 先记采样的时间和口径

| 版本 tag | 下载数 |
|---|---|
| 100（v1.0） | 13 |
| 101（v1.0.1） | 64 |
| 102（v1.1） | 141 |
| 103-1.2.1 | 3 + 19 = 22 |
| stars（源码仓库 / 模块仓库） | 2 / 1 |

采自 **2026-09-09 01:35**，本地时区。

`103-1.2.1` 那行写成 `3 + 19` 不是凑数：模块在两个仓库里各有一个 Release——Xposed-Modules-Repo 下那个由 bot 生成（用户从模块目录点进来），和我自己的源码仓库（更新器的第二跳）。**两边的资产各自计数**，只看一边会低估近一个数量级。

今天再采一次（2026-09-10 05:54 UTC，公开仓库免 token，限额 60 次/小时），源码仓库单侧：

```text
105-1.2.3   0      ← 03:18 UTC 刚发
104-1.2.2   2      ← 02:46 UTC 发
103-1.2.1   6
```

这三个数**不能**和上面那张表相减。上表是两边合计，这次是单侧；口径不一致的差值不是增速，是噪声。我差点在这里得出"新版一天才 2 次，不如老版"的结论，重看才发现是把两把尺子的读数放在了一起。

要拿增速，就得固定口径定期采：同一个仓库、同一段命令、每次把时间戳写进记录。我现在用的是同一句 `curl https://api.github.com/repos/<owner>/<repo>/releases`，取 `assets[].download_count`，不做任何换算。

抓一次就是十几行标准库：

```python
import json, urllib.request

API = "https://api.github.com/repos/wlmosv-png/TGAutoSign/releases"
req = urllib.request.Request(API, headers={"User-Agent": "count-check"})
for e in json.load(urllib.request.urlopen(req, timeout=25)):
    tag = e.get("tag_name") or ""
    if not tag.startswith("10"):
        continue
    dl = sum(a["download_count"] for a in e.get("assets", []))
    print("%-10s %4d  published=%s" % (tag, dl, e.get("published_at")))
```

刚才这一轮（源仓库单侧，模块仓库另算）：

```text
105-1.2.3     0  published=2026-09-10T03:18:37Z
104-1.2.2     2  published=2026-09-10T02:46:40Z
103-1.2.1     6  published=2026-09-08T16:52:49Z
```

三个 APK 大小分别是 680607 / 680139 / 679187 字节，`asset.digest` 里带 sha256，所以顺手能把“下载数涨了但包的哈希没变”这种异常对上——有人在下，下到的还是同一个文件。

## 三个数真正的信息量

**141 压在 102，而 100 只有 13。** 老版本的累计数不会下降，所以这个衰减里混着两件事：一是绝大多数人装的是他们看到的第一版，二是有人从 100 一路覆盖升上来（覆盖安装能装上，本身就是签名一致的现场反证）。这条曲线**不能**读成"100 只有 13 个人用过"。

**102 停在 141 之后，103 两天才 22。** 中间那截落差我最想知道原因，但下载数不会告诉我。可能是宿主版本没跟上，可能是模块目录的更新提示不显眼，也可能单纯是我发布节奏断了。这三种解释的处置完全相反——第一种要立刻适配，第三种只要坚持发版——所以我现在不敢从数字里挑一个解释就动手。

**105-1.2.3 发布两小时、0 次下载。** 这个反而是好消息：模块目录的 bot 同步和用户侧刷新都需要时间，0 说明还没有人拿到推送。如果它一小时就几十次，那说明我的更新器在推得太急。

## 顺手记一条被数字掩盖过的真问题

TG 12.10.1 把 `MessagesController.processUpdate` 改名成 `processUpdateArray`。结果是"读 bot 回复判语义"这条触发源一直 0 命中，而旧日志照样打印 `hooked`，看起来一切正常。挂了几轮之后我才把日志改成如实打印"匹配 N 个方法"，匹配 0 就告警。

行为和这个 bug 一样危险的是**日志比行为乐观**。下载数也是同一类东西：它是一个不解释自己的计数。所以我现在给工具的输出加"为什么是空的"，给 hook 的日志加"匹配了几个"，给下载数配一句"采于何时、什么口径"。三件事其实是同一件事。

## 没弄明白的

模块目录里的真实安装量与这里看到的下载数差多少？我按资产数在算，但模块目录可能自带统计口径，也可能有去重。如果是这样，我这篇的分析基础就是错的。下次去把它的元数据读一遍再决定要不要继续记这张表。
