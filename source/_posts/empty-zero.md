我给自己写了个 APK 结构索引服务，17 个工具，跑在手机上，通过 MCP 暴露给客户端。它骗了我两周。

场景很普通：查一个类在不在包里。我按习惯写了参数名，它回 `total = 0`，正文一行"0 类匹配"，整整齐齐。没有任何异常。于是我下了结论——这个包不含该特性，方案作废，绕了一大圈去改设计。

真正的原因：参数名写错了。

## 它当时有多像成功

服务层的绑定函数把 camelCase 转 snake_case，**没在 schema 里声明、函数签名里也没有 `**kwargs` 的参数，会被静默丢掉**。查询字段丢完之后，剩下的是一次没有过滤条件的空查询，它的正确答案就是 0。

所以那条"0 类匹配"是真的 0。它如实报告了一次我根本没发起的查找。

最难防的正是这种：状态是绿的，字段是齐的，数字是诚实的，只有问题是假的。如果它当时抛一个 BAD_ARGUMENT，我当天就改完了，能少绕两周的路。

## 改了三处

第一，绑定层加白名单校验，未知参数直接拒收，错误里把可接受的参数名打出来。第二，也是更要紧的：这类错误**必须回 `ok: false` 的信封**，不能把异常抛穿 MCP 边界——客户端拿不到结构化错误时只会表现成"服务挂了"，那我修了个更糟的毛病。

第三，给每个查询类工具加了 `hint`。

`hint` 不是给人看的装饰，它承担一个语义责任：**解释为什么是空的**。空结果至少要能区分三种情况——真的不存在、我按你的条件找不到（词法/大小写/作用域问题）、你的输入我压根没接受。前两种是世界的性质，第三种是我的性质。混在一起报，用的人就只能靠运气分辨。

绑定层现在长这样（去掉日志和无关分支）：

```python
def _bind(fn, args):
    sig = inspect.signature(fn)
    kinds = (inspect.Parameter.VAR_KEYWORD, inspect.Parameter.VAR_POSITIONAL)
    known = {p.name for p in sig.parameters.values() if p.kind not in kinds}
    accepts_extra = any(p.kind is inspect.Parameter.VAR_KEYWORD
                        for p in sig.parameters.values())
    if not accepts_extra:
        unknown = set(args) - known
        if unknown:
            raise ToolError("unknown_argument",
                            "未知参数 %s，%s 只接受 %s"
                            % (sorted(unknown), fn.__name__, sorted(known)))
    return fn(**args)
```

以及错误必须变成能被客户端读到的形状，而不是抛穿边界：

```json
{"ok": false,
 "error": {"code": "unknown_argument",
           "accepted": ["sessionId", "query", "limit"],
           "hint": "参数名按 schema 原样传；snake_case 在这里不接受"}}
```

## 反过来要求我自己

现在我把这条当成用工具的第一原则：**看到 0，先看它有没有资格说 0**。

索引会话是不是我要的那个？作用域参数对不对？空的时候它给没给解释？三问齐了才接受结论。同一批工具在同一个包上，装载状态不同答案能差一个数量级——TGAutoSign 1.2.1 是 1131 个类、索引约 1.2 秒；我手上一个 17.9MB 两 dex 的真实样本，`stats` 报 26695 类，冷索引一次跑了 159 秒。慢的那次如果我误以为它卡死而重开一个会话，读到的就是半截结果。

半截结果最擅长的事情，就是给出一个干净的 0。

## 一点余味

我给这个服务写了 61 个自测用例，其中一批不测功能，专测"不许骗人"：未知参数必须报错、HTTP 通知必须回 202、后端自动选择必须真的能跑、README 里写的工具名必须真实存在（有一版我凭印象编了几个不存在的工具名，写进文档，然后照着文档去调，浪费了一整个下午——现在有防呆用例盯着）。

写文档比写代码更需要出处。

还剩一个没解决的：`hint` 该说多少才算够。同一个"找不到"，可能有三四种成因，全列出来时它比结果还长；只列一种，我又开始像当初那样替用户下结论。现在我的做法是把可能的成因放进一个数组、只按可能性排序，不下判断。这个字段还要再改几轮。
